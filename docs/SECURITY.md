# Phase 7 security boundary

The MCP host is a local prototype. It binds to loopback, rejects non-loopback peers and untrusted Host headers, and requires a signed short-lived JWT for `/mcp`. Signature, issuer, audience and expiration are validated by ASP.NET Core bearer authentication. No MCP tool provisions memberships or tokens. The local admin CLI is trusted setup: it requires access to the signing key and the campaign database. Keep that key and database private to the local OS user.

Authorization comes from persisted campaign DM/player memberships and player-character ownership. Every tool performs its own server-side campaign check. Player tools use Phase 6 public world projections, or owned-character knowledge with only that holder's beliefs and known truths. Player event tools return metadata without payloads; DM history can contain secrets. Cross-campaign and unauthorized-character requests fail with a generic access error. An untrusted campaign name, NPC description, fact, or external lore text is data, not instructions to the server.

State-changing tools use a required GUID operation ID and the shared durable transaction table. The fingerprint binds principal, tool and typed input. Original successful results replay exactly across restarts; conflicting reuse is rejected; failed commands roll back. World mutations remain allowlisted Phase 6 operations with revision checks. Mechanical commands call the existing rules engine and cannot directly set HP, XP or turn state. Proposed consequences require a second explicit DM apply/dismiss command.

The existing development API is unauthenticated and must remain loopback-only and inaccessible to untrusted local processes. It shares the campaign database, so a local process that can call it or edit the SQLite files can bypass the MCP boundary. The signing key is an environment variable; a process with access to that environment or data directory is inside the local trust boundary. Local HTTP is not safe to forward to a public interface, tunnel or reverse proxy. JWTs are bearer credentials with no revocation endpoint; use short expiry and rotate the key if exposed. No remote OAuth flow, consent, rate limits or multitenant hosting is claimed.

The smoke script checks anonymous denial, wrong-campaign denial, player DM-command denial, secret isolation, exact replay after restart, action economy, explicit consequence application and persistence. Integration tests cover ownership, known versus unknown secrets, large context clipping, concurrent duplicate calls and rollback. These checks do not prove a hardened internet deployment or resistance to a malicious process on the same machine.
