# Phase 7 report — secure local MCP foundation

Phase 7 adds an authenticated MCP adapter over the existing D&D engine and a reproducible scripted campaign playtest. The engine remains authoritative for dice, combat, character resources, world state and persistence. The client supplies requests and narrative decisions; there are no built-in model calls or autonomous DM behavior.

## Architecture and dependencies

The new `DndEngine.Mcp` .NET 10 process uses the official `ModelContextProtocol.AspNetCore` **2.2.0** SDK with stateless Streamable HTTP at loopback `/mcp`. `Microsoft.AspNetCore.Authentication.JwtBearer` validates signed 15-minute local tokens. The host is separate from the unauthenticated development API and calls the existing Application services; it does not implement another rules engine. `CampaignAccessService` resolves campaign DM/player membership and player-character ownership from `campaign.db`. The trusted local CLI grants access and issues tokens. The new direct-call command runner uses the existing Phase 5 idempotency table and one SQLite transaction for a successful MCP command, audit and stored result.

Two additive campaign migrations, `20261009010000_Phase7McpAccess` and `20261009011000_Phase7Consequences`, add persisted `CampaignAccess`/`CharacterOwnership` rows and `NarrativeConsequences` records after the Phase 6 migration. Existing rules and campaign data remain in `rules.db` and `campaign.db`; no SRD pack or Phase 1–6 route changed. The consequence record uses the source event ID as its primary key. Application code validates that the source event exists, belongs to the campaign and has an eligible type before creating a proposal. The source event table itself was not rebuilt to add a new alternate key because that would risk older SQLite migrations.

See [MCP architecture](MCP_ARCHITECTURE.md), [tool catalog](MCP_TOOLS.md), [security boundary](SECURITY.md) and [DM context](DM_CONTEXT.md) for setup and contracts.

## Tools, context and consequence flow

The SDK discovers **30 typed tools**: 14 reads, 9 mechanical commands and 7 narrative commands. DM-only writes check persisted DM membership. Player reads use public world projections; character-specific actions and knowledge require ownership. Event history for players contains owned-character metadata, never narrative payloads. Commands require a stable GUID operation ID. Duplicate calls replay the original result; changed input conflicts, and failures roll back without a replacement random result.

`get_dm_context` deterministically selects campaign, character, active encounter, nearby NPCs, factions, relationships, active quests, facts, holder knowledge, events and unresolved consequences. It caps section counts and individual serialized entries and returns truncation metadata. Full detail is available through scoped read tools. Facts and events retain source IDs. The player context never receives unknown secret truth.

`MonsterDefeated` and `EncounterCompleted` are eligible for DM review. A DM may propose typed Phase 6 changes against one source event; proposal alone does not change the world. A later explicit apply or dismiss resolves it once. Apply commits the world revision, narrative audit events and the resolution atomically. The system does not infer motivations, relationship changes or quest progress from combat.

## Verification

Before implementation, restore/build/test passed with **227 tests** (148 domain, 10 application, 69 integration), and all five existing HTTP smoke scripts passed. After implementation, restore and solution build succeeded with **0 warnings and 0 errors**. The focused Phase 7 integration set passed **5/5**, including access isolation, context clipping, concurrent duplicate commands, rollback/restart replay, one-time consequence application and a Phase 6 database upgrade without lost world state. All five existing HTTP smokes passed again with the Phase 7 schema: base, combat, character, encounter and world. The final full-suite count is **232/232** (148 domain, 10 application, 74 integration).

`scripts/McpSmoke.ps1` starts isolated API and MCP processes, uses real JWTs and the official MCP SDK client, discovers 30 tools, and verifies anonymous denial, cross-campaign denial, DM/player separation, unowned character denial, malformed input handling, player event-payload redaction and secret isolation. Its seeded scene has a guardian, scout, location, NPC, active quest, secret and pinned skeleton. The player client retrieves context, makes a skill check and attacks. The engine denies a second action in the same turn. The DM client completes the encounter and explicitly proposes and applies a source-linked narrative consequence. The script restarts MCP and checks context recovery and exact dice replay. Evidence is saved under `artifacts/mcp-smoke-*/result.json`; these folders are ignored by Git.

This is a **deterministic scripted MCP client playtest**, not a ChatGPT or other external-model playtest. No model generated narration, made independent decisions or demonstrated prompt-injection resistance. The SDK playtest exercises a check and weapon attacks; it discovers but does not invoke `cast_spell` or `use_item`. The existing HTTP encounter smoke exercises their underlying engine services. The MCP smoke's fixed scenario pre-wounds the skeleton to one HP to keep the encounter short; the attack roll itself still comes from the engine and may take more than one attempt.

## ChatGPT compatibility and limitations

The local host was not connected to ChatGPT. OpenAI's current [MCP app guidance](https://help.openai.com/en/articles/12584461-developer-mode-and-mcp-apps-in-chatgpt) says ChatGPT connects to **remote MCP servers** rather than directly to local ones; a private/local service needs a supported secure tunnel. It also says **ChatGPT Pro** can connect custom MCPs with read/fetch permissions, while full write/modify MCP support is currently for Business and Enterprise/Edu. Therefore this write-heavy local host is **not verified as a usable ChatGPT Pro DM connector**. Remote deployment would require the [MCP authorization flow](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization), HTTPS, OAuth consent/PKCE, protected-resource metadata, access isolation and tests. The local JWT approach is not a substitute for those controls.

For a later real-client test, run `scripts/McpSmoke.ps1` and open its `result.json`. Reuse its `directory/data` as `DataDirectory`, configure a new random `DND_MCP_AUTH_KEY` as in [MCP architecture](MCP_ARCHITECTURE.md), then issue fresh tokens using `admin token` for its `dmSubjectId` and `playerSubjectId`. Start the MCP host on loopback and configure a local MCP-capable client with `/mcp` and the appropriate bearer token. In separate DM and player sessions: discover tools; ask the DM to read context and interpret the completed encounter; ask the player to read context and attempt to access the secret; have the DM explicitly apply a new supported world change with a stable operation ID; retry that ID; restart the host and reread state and audit history. Compare narrated claims with tool results and recorded event IDs. Do not use this loopback JWT host as a public ChatGPT endpoint.

Unsupported operations remain explicit: arbitrary HP/XP edits, generic SQL or script execution, map-based position proof, unsupported spells/items/monster behaviors, lore ingestion and autonomous AI decisions. User-supplied spatial facts such as distance and visibility still require human adjudication. Context pages can omit older relevant records, so callers must advance cursors or use specific reads. The existing loopback development API and filesystem remain inside the local trust boundary. These limits, and any remote OAuth work, are recommended Phase 8 candidates only with separate approval; **Phase 8 has not begun**.
