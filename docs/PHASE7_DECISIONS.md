# Phase 7 architecture decisions

Recorded after auditing the Phase 1–6 services, migrations, API, reports and baseline checks, and reviewing the official C# MCP SDK, MCP authorization specification and current ChatGPT documentation; before Phase 7 implementation.

1. **Separate host:** A new `DndEngine.Mcp` ASP.NET Core process hosts only Streamable HTTP MCP, not the unauthenticated development API. It binds to loopback and rejects non-loopback connections and untrusted Host headers. No remote MCP endpoint is claimed.
2. **SDK:** Pin the official `ModelContextProtocol.AspNetCore` package, use its stateless HTTP transport and a deterministic SDK client for discovery/invocation tests. Tool classes call existing Application services, never EF directly except dedicated infrastructure for identity, replay and consequence records.
3. **Local identity:** Use ASP.NET Core bearer authentication with signed, short-lived JWTs from a separately configured local issuer/key; validate issuer, audience, signature and expiry. Principal IDs come only from validated claims. Persist per-campaign DM/player memberships and player-character ownership in `campaign.db`. A server-side authorization service checks these on every tool call; an unbound role claim gives no access. Provisioning is a trusted local setup operation, not an MCP tool. OAuth authorization-code/PKCE, resource metadata, public HTTPS and ChatGPT connectivity remain a documented remote design, not an untested deployment.
4. **Least disclosure:** DM tools require campaign DM membership. Player reads and actions require campaign membership and, for character-specific actions, ownership. Player world data comes from the Phase 6 allowlist; player event history excludes narrative payloads. Player knowledge is restricted to owned characters and can show their own beliefs without exposing hidden world truth or other holders. Errors use generic authorization text.
5. **Command boundary:** Extend the Phase 5 `IdempotencyOperations` table with a direct-call transaction runner. Each MCP mutation requires a stable operation ID and fingerprints tool name, authenticated principal and canonical typed input. The claim, domain changes/events and stored successful result commit in one SQLite transaction. Replays return the stored result; differing input conflicts; failed calls roll back. The existing HTTP middleware remains compatible.
6. **Context:** A bounded service builds DM/player context from existing authoritative services with deterministic ordering, cursors and truncation metadata. It does not send a full database dump. Stored source IDs distinguish facts and events from narrative interpretation.
7. **Consequences:** Eligible mechanical events can be reviewed as pending work without inventing world changes. A source event gets at most one resolved record (applied or dismissed). Application applies typed Phase 6 world changes and records resolution atomically. The workflow is DM-only and never implies that every mechanical event requires a consequence.
8. **Scope:** Expose a bounded, truthful tool catalog. Commands with no supported engine use case return an explicit unsupported error. No built-in model calls, autonomous decisions, generic SQL/script tools, lore ingestion or Phase 8 work.
