# Phase 5 report — monsters, inventory and playable encounters

Phase 5 delivers a bounded, persistent encounter workflow on top of Phases 1–4. An HTTP smoke run created a campaign, a choice-based PC and a combat guardian, spawned two Skeletons and a Priest Acolyte, rolled initiative, used a weapon, a potion and Healing Word, defeated the monsters, completed the encounter as Victory, awarded their 150 printed XP to the PC, transferred a Shortsword as loot, restarted the API, and replayed the XP command without another award or event.

## Baseline and research

Before Phase 5 changes, `dotnet restore`, `dotnet build` and `dotnet test` passed: 148 Domain, 10 Application and 55 Integration tests. The Phase 1, Combat and Character smoke scripts also passed on isolated databases. The important gap was that Phase 2 accepted manually imported combatants but had no pinned monster definitions/instances; Phase 3 owned an unquantified item list; Phase 4 had a bounded spell engine but no playable reward/consumable workflow. Mutating API calls had no durable operation replay.

The source is the [official SRD 5.2.1 PDF](https://media.dndbeyond.com/compendium-images/srd/5.2/SRD_CC_v5.2.1.pdf): Goblin Minion printed p. 290, Priest Acolyte p. 316, Skeleton pp. 325–326, Potion of Healing pp. 99 and 236, and XP/challenge rules pp. 22, 181 and 255. The three monster stat blocks and one item entry are adapted into a small mechanical pack. The existing [attribution notice](../ATTRIBUTION.md) identifies the SRD and CC BY 4.0; this project does not include a setting/lore license or a license for the original code.

## Implemented

- `rules.db.MonsterPacks` contains a version-1, hash-checked Goblin Minion, Skeleton and Priest Acolyte pack. Definitions include identity/type/size/alignment/CR/XP, scores, HP/AC/speed, saves/skills/senses/languages, defenses, gear and action/spell support flags. Import validates pack identities, stats, referenced gear/weapons and supported spell mapping; a changed installed hash is refused.
- `campaign.db.MonsterInstances` pins individual creatures to monster pack 1 and spell pack 6. HP, conditions, supported weapons/ammunition and inventory use the existing character and combat projections. Identical monsters have distinct state. Goblin dagger and Skeleton shortsword/shortbow attacks reuse `WeaponAttackResolver`; Priest Acolyte's one-per-day Divine Aid Healing Word reuses `SpellCombatResolver`. Unsupported actions/spells have explicit deferred reasons. `MonsterDefeated` is emitted on a live-to-dead combat transition, not on every later command.
- `InventoryStates` owns item instance IDs, quantities, equipment flags and copper. Choice-based character progression and combat profile projections are updated together. Supported commands acquire, remove, transfer between owners, equip/unequip, change copper, drop/pick up a recoverable `DroppedItem`, and consume Potion of Healing. Stacks split/merge without duplicating quantity. Outside-combat potion use heals the owner; encounter use consumes a Bonus Action and may heal a living target within caller-supplied 5-foot distance. Transfers advance both owner revisions and commit one event with both identities.
- `CombatEncounter` remains the single initiative/turn/attack/damage engine. Explicit `/complete` accepts Victory, Defeat, Retreat or Other; it never infers an outcome solely from HP. Completion stores defeated monster IDs and their printed XP pool in `EncounterRewards` alongside the encounter transition/event. XP allocation is a bounded ledger for participating PCs, with no automatic level advancement. Loot award transfers an actual remaining item from a defeated monster to a participating PC. The legacy `/end` route remains available for older clients and does not open the Phase 5 reward ledger.
- New mutating endpoints require `X-Operation-Id`. A reusable HTTP middleware claims the GUID and stores a fingerprint plus original successful response in `IdempotencyOperations` within the same campaign SQLite transaction as the command. Identical retries replay the response across restart. Changed payloads get 409. Concurrent duplicates wait for the first committed result or receive a bounded retryable conflict. Failed commands roll back the claim. Legacy routes accept the header optionally to preserve Phase 1–4 clients.
- Audit events include `MonsterSpawned`, `MonsterDefeated`, `EncounterCompleted`, `ItemAcquired`, `ItemTransferred`, `ItemDropped`, `ItemRemoved`, `ItemConsumed`, `EquipmentChanged`, `CurrencyChanged`, `LootAwarded` and `ExperienceAwarded`. Combat action events retain dice and HP changes. Encounter completion includes the chosen outcome and eligible XP, and loot/XP records identify recipients and amounts.

## API and storage

The typed routes and example payloads are in [Encounter API](ENCOUNTER_API.md). The new API covers monster definitions/instances/enrollment, item definitions and inventory, combat potion use, explicit completion, reward inspection, loot and XP. Existing API contracts remain callable.

Two additive EF migrations are `20261008100000_Phase5MonsterCatalog` for `MonsterPacks` and `EncounterItemPacks` in `rules.db`, and `20261008100000_Phase5MonsterInstances` for `MonsterInstances`, `InventoryStates`, `DroppedItems`, `EncounterRewards` and `IdempotencyOperations` in `campaign.db`. Existing tables/data are preserved. The local pinned `dotnet-ef` CLI could not be restored through restricted NuGet access, so migrations and snapshots were authored directly and checked by `HasPendingModelChanges()` integration assertions. Startup still uses `MigrateAsync`, never `EnsureCreated`.

Inventory, transfer, drop/pickup, potion use, monster spawn, combat state/HP/spells/defeat and encounter completion each persist state and events in one SQLite transaction. Character/encounter/reward revision checks reject stale work. The HTTP operation transaction encloses these saves and the stored response. A timeout should be retried with the same GUID and identical request bytes; the caller must reload after a 409. No random outcome is silently rerolled by the application.

## Verification

Final `dotnet restore DndEngine.slnx` and `dotnet build DndEngine.slnx --no-restore` passed with zero warnings/errors. The full suite passed: **148 Domain, 10 Application and 65 Integration tests (223 total)**. Phase 5 integration coverage includes pack import/snapshot validation, independent monster instances, initiative and monster weapon attacks, Priest Acolyte Healing Word resource use, Skeleton condition immunity and bludgeoning vulnerability, defeat and manual Retreat/Victory, inventory quantity/ownership/transfer/equipment/currency/drop/pickup, potion use, loot/XP, stale revisions, a forced SQLite transaction rollback, concurrent duplicate API operations, changed-payload rejection, exact replay after restart and persistence. Earlier Phase 1–4 tests remain green.

All four process smoke scripts passed with isolated databases: `Smoke.ps1`, `CombatSmoke.ps1`, `CharacterSmoke.ps1`, and `EncounterSmoke.ps1`. The most recent Phase 5 evidence is `artifacts/encounter-smoke-20261008-223728/result.json` (ignored runtime output): three monsters defeated, weapon attacks, spell cast and item use observed, 150 XP awarded, Shortsword loot persisted, restart succeeded, and XP replay left one award/event. The old smoke scripts likewise passed after the changes. Smoke tests establish the bounded workflow and persistence; they are not full SRD parity or balance tests.

The post-implementation review closed these issues: level-1 Paladins/Rangers no longer receive spell slots before Spellcasting; Poison Spray uses a Constitution save in new immutable spell pack 7 (existing pack 6 stays pinned); Circle of Death consumes one black pearl powder item in the same encounter transaction as the cast; completion handles manually imported monsters without inventing catalog XP; generic health/check commands reject enrolled combatants; and older weapon grants now appear in inventory. Review also tightened pinned-monster mutation and ammunition validation and made equipped armor claimable from a defeated Acolyte. The focused regression tests and all four smoke scripts passed after the fixes.

## Deliberate limits and deviations

- This is a three-monster catalog and one supplemental consumable, not the full SRD. Goblin Nimble Escape, Priest Acolyte's radiant mace rider/Radiant Flame and other unsupported spells or reactions are marked deferred. General monster special abilities and spellcasting are not silently approximated.
- Priest Acolyte's Divine Aid use is consumed and persisted once; automatic renewal on a later day/long rest is deferred because the engine does not model monster rest cycles. A new monster instance starts with its own use.
- The caller still adjudicates distance, sight, cover and tactics. There are no coordinates, pathfinding, held-hand state, encumbrance, purchase/sale prices, restocking, treasure tables or autonomous NPC behavior. The potion's listed price is catalog data, not a purchase transaction.
- XP is a validated, auditable reward ledger, not automatic character progression. Level-up remains the explicit Phase 3 operation. Loot is limited to remaining owned item instances of defeated monsters; no generated treasure is invented.
- New Phase 5 commands require an operation ID; older mutating routes only accept it optionally for compatibility. The fingerprint compares exact request bytes, so semantically equivalent JSON formatting is a different payload for the same GUID. `/combat/{id}/end` remains as a legacy completion path without a reward ledger; use `/complete` for Phase 5 rewards.
- Item definitions are pinned in supplemental pack 1, but existing Phase 3 character item definitions remain in their original pinned pack. Only Potion of Healing is automated as a consumable. A monster's printed AC is retained when its gear changes; altering monster equipment behavior is rejected or limited to ordinary gear rather than recalculating an unsupported stat block.

Recommended Phase 6 scope, **only after separate approval**, is a small authored campaign/world-state slice that consumes these events without changing mechanical truth: named NPC identity, location/quest facts and explicit consequence events. A separate later mechanical increment should expand immutable monster/spell/item packs, held-object and spatial adjudication, and package/economy rules with dedicated parity tests. No Phase 6 implementation is included here.
